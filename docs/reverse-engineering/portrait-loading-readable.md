# 头像资源加载与选择

## 资源与调用链

`0x42BC2B` 将 `FACE.E5` 加载到 `0x4AC538`，使用通用容器初始化器 `0x41FB35`。`0x41FC89(container,index,destination)` 按索引读取并解压资源。

本次逐条解码得到 228 条资源，全部为 5120 字节。剧情头像绘制函数 `0x432ED9` 和另一显示路径 `0x46D749` 明确传入 64×80，因此资源尺寸不再需要猜测。武将情报更新函数 `0x478688` 也是通过同一头像选择函数及容器加载头像。

## 选择规则

`0x4075A7` 的输入是角色运行时记录。角色身份为 `word(unit+0) & 0xFFF`，普通头像索引取 `int32(unit+4)+7`。不能直接用列表序号替代此字段。

公共状态基址为 `0x4B0770`，以下 flags 为 `byte(base+0x11)`，phase 为 `byte(base+6)`。这些名称是工具中的中性称呼，尚未证明每个位的完整剧情语义。

| 角色身份 | 原版选择 |
|---|---|
| 0 | phase < 2 使用起始索引 0，否则 4；flags 低四位为 1/2/3 时加相应值，其余加 0 |
| 1 | flags 低四位为 4 时用 224；否则若 bit 7 为零用 223，否则普通索引 |
| 35 | flags bit 4 置位时用 214，否则普通索引 |
| 8 | flags bit 5 置位时用 226，否则普通索引 |
| 4 | flags bit 6 置位时用 227，否则普通索引 |
| 其他 | 普通索引 |

## 原生交叉验证与复现

运行：

```powershell
python tools/export_portrait_index.py
python tools/verify_portrait_index_native.py
```

第一条生成 `analysis/portrait-index.json`：资源尺寸、解压内容 SHA256、字段来源和选择示例。

第二条在挂起的原版进程中直接调用 `0x4075A7`，进程从不恢复执行，不打开游戏界面或播放音乐，并在 finally 中终止。对六种身份、四个存储头像值、四个 phase 和全部 256 个 flags，共 24576 个组合，Python 规则与原版返回值 24576/24576 一致。结果见 `analysis/native-portrait-index-validation.json`。

这验证的是选择函数，不是完整 UI 或全部头像显示。已进一步定位 EEX opcode32 的公共标志写入，10752 组原生分派器验证通过；详见 `eex-opcode32-portrait-flags.md`。phase 已关联到 opcode103 章节入口和 opcode58 阶段分支，1315组原生验证通过，见 `eex-portrait-chapter-phase.md`；其他潜在写入和完整剧情运行仍需追踪。

## 绘制与透明约定的进一步验证

`0x478688` 先设置绘制上下文 1、像素模式 7，再调用 `0x47D1F1(4,0x12,0)`。`0x47E09B` 在模式 7 下直接使用原始 8 位索引数据，不执行 4 位像素展开；绘制模式 4 分派到 `0x47F740`。

`0x47F740` 在像素模式 7 下跳过索引 0，其余字节原样写入目标。不是按 RGB 粉色去透明，也不是所有低四位为零的索引都透明。

```powershell
python tools/verify_portrait_blit_native.py
python tools/analyze_portrait_palettes.py
```

原生 blit 探针用全部 228 张解码头像实际调用 `0x47F740`，源步长 64、目标步长 72，检查每个像素及每行额外 8 字节未被修改。228/228 通过。见 `native-portrait-blit-validation.json`。这不包含窗口初始化、裁切及最终调色板上传。

## 场景调色板不能忽略

全部头像合计使用 168 个索引。对 PMPALET 与 SPALET 的全部 173 项调色板，以 PMPALET 第 0 项为基线、忽略透明索引 0、比较保留高四位后的可见颜色，只有 40 项完全相同。至少部分场景的头像用色确实存在差异，不能无条件将一套基线 PNG 当成全游戏正确结果。

`portrait-palette-analysis.json` 给出了每个调色板发生变化的头像索引。`analysis/portraits/0000.png` 至 `0227.png` 是 64×80 的基线预览：使用 PMPALET 第 0 项并令索引 0 透明。它们便于检查资源，不是已经通过全部场景验证的最终 Web 美术。

进一步统计发现，两套容器的 173 项调色板对头像实际用色仅形成两组：PMPALET 0 为第一组代表（40 项）；PMPALET 40 为第二组代表（133 项）。差异只涉及索引 174–178，实际受影响的头像资源是 12、21、176、179、184、185、214、215、225，共 9 张。SPALET 31 属第二组。

还需特别区分“绘制器支持透明”与“资源有透明像素”：全部 228 张头像中索引 0 像素总数是 **0**。这些 FACE 图像按此路径绘制是完整矩形。不能像某些图标那样把 RGB 粉色抠除；预览的 `transparency=0` 不会抹去任何实际 FACE 像素。

## 活动调色板与窗口上下文

以下静态调用链已经确定：

- `0x40BC37` 根据场景模式取背景索引，部分模式分别加 0x72 或 0x28，再调用 `0x41E050(index,0)` 载入 PMPALET。
- `0x44D092`、`0x44D427` 使用状态记录首字节作为索引，调用 `0x41E050(index,1)` 载入 SPALET。
- `0x41E050` 将资源写入 `0x497770`，每个字节右移 4 位，建立颜色查找表。
- `0x41E1F3` 将 `0x497770+30` 的 236 个颜色上传到索引 10–245；`0x41E405` 完成渐亮后也上传同一完整范围。
- `0x47E867` 维护共享的颜色表。在 DIB 路径中循环所有已创建的绘制上下文，通过 `0x47F402` 调用 `SetDIBColorTable`。不是每个头像窗口都拥有独立固定的 FACE 调色板。
- `0x478688` 切换上下文 1 绘制头像后，`0x460863` 将头像窗口放入武将情报控件 0x434 并居中显示；此链上没有单独重新加载头像调色板的调用。

原生存储颜色三字节为 `[B,R,G]`。上传函数生成 RGBQUAD `[B,G,R,保留字节]`，以及 PALETTEENTRY `[R,G,B,保留字节]`；shift=4 时把四位通道放大为高四位，最大值 240，不是 255。

```powershell
python tools/verify_palette_upload_native.py
```

该探针实际执行 `0x47E867`，对全部 173 项真实调色板、上下文 0 和 1 共 346 组，逐字节检查两张颜色表、未更新索引/保留字节，以及向两个 DIB 上下文传播的调用。346/346 通过。窗口重绘和 DIB 写出被拦截，进程没有恢复主线程，不会展示游戏或发声。结果见 `native-palette-upload-validation.json`。

这证明普通头像绘制应与当前已上传的共享场景调色板一致。仍缺实际完整游戏轨迹对特殊头像、阶段变化和颜色切换时点的联合覆盖，不能将全部调色板索引都当成每张头像必然可达的显示组合。Web 可保留可读索引像素数据和调色板，在运行时按场景转换；也可以对这两组导出变体，但需按原版状态选择，不能把其中一组全局固定使用。
