# EEX Side-Effect Handler Semantics

Direct pseudocode confirms three high-value handlers:

| Opcode | Handler | Native behavior | Return |
|---:|---:|---|---:|
| 7 | `0x415C46` | Read global `0x4AE4C0`; if nonzero clear it and report that a pending global event existed | boolean old-value |
| 28 | `0x413EBD` | Read mode/status from `0x40B913`; dispatch to `0x428B11` when it equals 2, otherwise `0x41E405` | `1` |
| 106 | `0x416DFA` | If `0x40B922()` reports the relevant runtime mode, clear global `0x4B3D10` | `1` |

These are stronger than opcode-name guesses: the global reads/writes and branch calls are explicit in recovered native pseudocode and match the side-effect candidate index generated by `tools/export_eex_handler_semantics.py`.

Native synthetic validation now confirms opcode 7 (`analysis/native-eex-side-effect-validation.json`): setting `0x4AE4C0` to 1 returns 1 and clears it; setting it to 0 returns 0 and leaves it clear. This is a direct runtime confirmation of the static handler semantics without requiring story GUI progression.

The same synthetic run covers both opcode 106 branches. With `0x4AC63C != 3`, setting `0x4B3D10=0x7A` returns `1` and leaves it unchanged; with `0x4AC63C=3`, the same call returns `1` and clears it to zero. `0x40B922`/`0x40B8B0` confirm that this mode condition is a direct global-byte test.
